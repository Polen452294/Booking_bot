# Phase 7.5B: Telegram flow заявок и диалогов

## Клиент

FIXED: услуга → дата → слот → телефон → подтверждение → Appointment. Дополнительная
заявка не создаётся. NEGOTIABLE: описание/фото/документ → необязательные дополнительные
файлы → «Отправить заявку» → телефон, если ещё не сохранён → BookingRequest и Conversation.
Календарь доступен после принятия условий. FROM показывает стартовую цену и два пути:
«Записаться» открывает старый календарь, «Сначала обсудить» открывает flow заявки.
Повторная запись также учитывает pricing_mode услуги.

До отправки данные находятся в FSM, без черновика в БД. Создание заявки, сохранение
приложений и submit выполняются атомарно; мастер получает один job о новой заявке.
Первый текст становится описанием и первым сообщением. Фото/документ может быть первым
вводом: подпись служит описанием, либо сохраняется понятное описание медиа.
Фото не обязательно. Разрешено до 30 дополнительных сообщений/файлов на этапе создания.

«Мои заявки» содержит «Активные» и «Завершённые». Во втором разделе находятся booked,
cancelled и closed; сама запись имеет независимый lifecycle. Списки идут страницами
по 20 заявок. Карточка показывает услугу, статус, последнюю цену/обсуждение, дату,
короткое последнее сообщение и unread. Длинное сообщение целиком доступно в диалоге.
Кнопки предлагают диалог, последнее предложение, выбор времени, подтверждаемую отмену
и переход к созданной записи согласно текущему состоянию.

## Мастер

В /cabinet и кабинете есть «Заявки и диалоги» с суммарным badge. Inbox содержит:
«Новые» (waiting_master, история ещё не открыта мастером), «Ждут моего ответа»,
«Ждут клиента», «Согласованы», «Закрытые». Новая заявка может входить и в раздел
ожидающих ответа. Статус terms_proposed входит в ожидающие клиента.

Элемент списка показывает имя клиента, услугу, статус, дату и unread. Карточка добавляет
контакт и полное описание отдельным сообщением, чтобы не превысить лимит Telegram.
Действия: диалог, предложение/изменение цены, подтверждаемое закрытие, переход к записи.
Закрытие booked-заявки закрывает только conversation, сохраняя Appointment.

## Диалог и медиа

Открытие показывает последние 20 сообщений. «Показать предыдущие» использует sequence
cursor и существующий pagination service. Есть переход к последним сообщениям,
карточке и главному меню. Стороны подписаны «Вы», «Мастер», «Клиент»; system events
отделены визуально и содержат читаемую цену/дату вместо внутренних identifiers.
Короткие текстовые сообщения объединяются в блоки до 4096 символов после HTML parsing,
сохраняя порядок и границы сообщений. Это уменьшает число вызовов Telegram API;
длинные сообщения сохраняются целиком, без обрезки.

«Написать мастеру»/«Ответить» включает RequestStates.reply для выбранной заявки.
Одиночный text/photo/document сохраняется через ConversationService, после чего ввод
завершается. Альбом сохраняет все отдельные Telegram updates и оставляет ввод активным
до «Готово / Назад». Во время сборки альбома нет ответа на каждую фотографию.
При просмотре соседние фото одного автора объединяются штатным sendMediaGroup,
до 10 фото за один вызов. Оригинальный media_group_id не сохраняется: Phase 7.5A
хранит file_id/file_unique_id/caption, поэтому границы исходных альбомов не восстанавливаются.
Документы показываются отдельными сообщениями. Файлы не скачиваются локально.

Нет forwardMessage, прямого relay и автоматического раскрытия Telegram usernames/IDs.
У связанной с заявкой записи кнопка контакта ведёт во внутренний диалог; прежний
контакт обычной FIXED-записи сохранён. Телефон видит назначенный мастер в карточке заказа.

Лимиты: text/description 4000, comment 2000 символов; превышение объясняется пользователю,
текст не обрезается. Стикеры, voice, video, location и contact в reply/request input
не отправляются в conversation; пользователь получает список допустимых типов.
Contact разрешён только на отдельном шаге телефона; чужой контакт отклоняется.

/start и /cancel выходят из FSM, освобождают hold и убирают reply-клавиатуру.
Invite `/start master_<payload>` сохранён. Есть «Отмена»/«Назад» и главное меню.
Redis TTL текущего приложения дополнительно ограничивает срок FSM.

## Цена и запись

Мастер вводит стоимость в currency услуги (до двух десятичных знаков, minor units),
затем комментарий или «Пропустить». Preview содержит «Отправить клиенту», «Изменить»,
«Отмена». Proposal создаётся только после подтверждения. Ноль разрешён backend;
отрицательные и чрезмерные значения запрещены. Форматирование общее, без float.

Клиент видит «Принять», «Обсудить» и при открытии предложения «Отклонить».
«Обсудить» открывает историю и сохраняет PENDING. Accept/reject передаёт proposal UUID
в сервис, который сам находит заявку, проверяет участника, актуальную revision/status
и блокирует запись. Старое/повторное предложение показывает «уже неактуально».
Новый proposal supersedes старый PENDING; история показывает старую и новую суммы.

После terms_accepted доступны прежние даты/слоты/подтверждение. Request UUID хранится
в FSM после service authorization. На выборе слота и финальном подтверждении условия
и actor проверяются заново BookingRequestService. Конфликт не теряет заявку и историю.
Appointment сохраняет согласованную цену и unique booking_request_id, а request становится
booked. System event показывает время в timezone deployment и цену.
В обеих карточках записи есть кнопка conversation; сообщения после записи разрешены,
пока conversation открыта.

## Unread, уведомления и ошибки

Badge считается сервисом по доступным заявкам. Открытие карточки и доставка push не
сбрасывают unread. mark_read вызывается после успешного показа страницы истории и
использует последнюю показанную sequence. Курсор не уменьшается при чтении старой страницы;
ошибка доставки истории оставляет unread. Собственные сообщения не увеличивают badge.

Новая заявка, сообщения обеих сторон, proposal, accept/reject и отмена создают существующие
NotificationJob в domain transaction. Worker проверяет доступ, preferences и отправляет
новое Bot API сообщение с кнопкой конкретной заявки/диалога. Retry/backoff и claim ownership
прежние. Ошибка уведомления не откатывает уже созданное предложение.
Без надёжного presence push не подавляется: отдельные сообщения альбома могут создать
несколько уведомлений. Exactly-once доставки в Telegram нет.

Callbacks короткие (<64 bytes), IDs не доказывают доступ. Master inbox отдельно проверяет
активного зарегистрированного мастера deployment; остальные операции используют access
control сервисов. Повтор updates обрабатывается существующим webhook receipt/lease,
нового механизма deduplication нет. Domain locks и unique constraints защищают Accept
и booking. Ожидаемые ошибки показывают понятный ответ. editMessageText при невозможности
редактирования отправляет новый экран; «message is not modified» безопасно игнорируется.

## Проверки

`tests/test_conversation_ui.py`: цены, лимит callbacks, escaping, system event/timezone.
`tests/test_requests_telegram_integration.py`: настоящий dispatcher/webhook, PostgreSQL,
Redis и замоканный Telegram API; полный E2E, FIXED/FROM, inbox, ownership, stale proposal,
FSM commands, media albums, unread, close/cancel, slot conflict, retry и double Accept.
`tests/test_conversations_integration.py`: предыдущие domain/security/concurrency проверки.

Дополнительный E2E dump/restore включается переменной
`BOOKING_TEST_POSTGRES_CONTAINER=booking-phase75b-postgres` только для disposable
`127.0.0.1:55432/booking`. Сравниваются полные строки шести связанных таблиц после
восстановления в новую UUID test database; исходная БД не меняется.
Отдельный `tests/disaster_recovery_smoke.py` проверяет BackupManager и восстановление
полного deployment, health и изоляцию второго deployment.

Phase 7.5C также допускает `booking-phase75c-*` контейнер в том же isolated profile.
После dump/restore старые proposal callbacks проверяются against восстановленного
BOOKED request и не меняют строки. Полный двухпользовательский сценарий включает
15k → обсуждение → 17k → stale accept 15k → accept 17k → слот → appointment → диалог.

`test_requests_hardening_integration.py` проверяет отказ commit при create/reply/
propose/accept/cancel/book: до commit отсутствуют success screen и toast, FSM
остаётся доступным для retry того же update. При ошибке UI после commit доменная
операция сохраняется вместе с outbox; `/start` и «Мои заявки» возвращают текущие данные.
Изолированная потеря Redis удаляет runtime/FSM/cache, но не PostgreSQL receipt,
history, proposal или appointment. Pending ввод до отправки заявки может быть потерян.

Runbook и ограничения: [conversations-operations.md](conversations-operations.md).

Проверка живым Telegram клиентом/реальным токеном в автоматизированный E2E не входит.
Payments, voice/video, editing/deletion, web chat, группы и multiple masters не реализованы.
