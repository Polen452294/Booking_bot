## Main features

Booking_bot помогает одному специалисту принимать записи и общаться с клиентами
через Telegram. Для каждого бизнеса создаётся отдельный deployment и бот.

- Услуги с фиксированной ценой, ценой «от» и согласованием стоимости:
  FIXED, FROM и NEGOTIABLE.
- Выбор свободного времени с защитой от двойной записи; просмотр, перенос,
  отмена и календарный экспорт клиентских записей.
- Кабинет специалиста: услуги, график, выходные и блокировки, ручные записи,
  внутренние заметки, статистика и Excel.
- Личная переписка до и после записи: текст, фотографии, документы и unread.
- Предложения цены и принятие актуальных условий. Согласованная цена сохраняется
  в записи и не меняется при изменении услуги.
- Уведомления и напоминания, PostgreSQL/Redis, HTTPS/webhook, отдельный worker.
- `bookingctl`: несколько изолированных deployments, backup/restore,
  versioned updates с обязательным backup, recovery и monitoring.

## Production requirements

Целевая OS: Ubuntu Server 24.04 LTS x86_64 с Docker Engine, Compose plugin
и systemd. Полная qualification этой платформы ещё не завершена.
Нужны отдельный Telegram bot, домен/DNS, публичный HTTPS с production
Let's Encrypt и доступ к Telegram API/GHCR. Публичные порты: согласованный SSH,
80 и 443; внутренние API/PostgreSQL/Redis/Docker API остаются закрытыми.

Устанавливается именно опубликованный image
`ghcr.io/polen452294/booking-bot:1.0.0`; production deployment фиксирует его
immutable image ID. Registry digest и commit будут приложены в
`release-manifest.json`. Одной публикации недостаточно для статуса RELEASED.

Для backup нужны свободное место, защищённая off-host copy и проверенный restore.
Monitoring alerts используют отдельные credentials. Ресурсы VPS проверяются
на фактической нагрузке; универсальные CPU/RAM нормы не заявлены.

Документация: [установка](../new-client.md),
[production](../production-deployment.md), [передача клиенту](../client-handover-checklist.md),
[backup/restore](../backup-restore.md), [monitoring](../monitoring.md).

## Upgrade notes

Перед upgrade обновите host CLI штатным способом и проверьте текущую версию,
verified backup и доступность release images. Update выполняется через
`bookingctl update CLIENT --version 1.0.0` с предварительным `--dry-run`.
Только более новая версия допускается; RC → stable поддерживается.
После update подтвердите doctor, version, Telegram smoke и production-check.

Ожидаемая Alembic head: `c75a01d29f10`, как у текущего RC. Для старой
pre-conversations БД применяются миграции; прежние услуги получают FIXED,
история/записи сохраняются. При совпадении schema head восстановление может
использовать application rollback; при изменении schema требуется verified
restore, автоматический downgrade запрещён.

Update приложения не обновляет storage images автоматически. Процедура:
[updates](../updates.md), [rollback](../rollback.md).
Опубликованные `1.0.0` tag/image не переписываются; исправления выходят в `1.0.1`.

## Known limitations

- Один специалист, Telegram bot, PostgreSQL и Redis на deployment.
- Нет online payments/deposits, CRM, web admin, AI и multi-master.
- Conversations: text/photo/document; нет voice/video/sticker, группового/web chat,
  редактирования и удаления сообщений. Media хранится как Telegram IDs/metadata.
- Redis/FSM черновики могут теряться; durable история и цены хранятся в PostgreSQL.
- Telegram delivery не обеспечивает true exactly-once при потерянном acknowledgement
  или restore; внешние сообщения при восстановлении БД не откатываются.
- Restore требует controlled downtime и возвращает данные к выбранному backup.
- Windows, ARM64 и Debian production support не заявлены.
- Управление одним registry с нескольких независимых hosts не поддерживается.
